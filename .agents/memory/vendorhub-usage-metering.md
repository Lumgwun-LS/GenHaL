name: VendorHub usage metering & quota enforcement
description: How metered resource usage (AI gen, voice minutes, SMS, email) is tracked, billing periods computed, and quotas enforced atomically across VendorHub.
---

## Billing period model
- No live per-action sync with Stripe/Paystack subscription periods (too expensive). Instead each vendor has a local period anchor that only moves on an actual tier change (upgrade/downgrade/cancel), not on every renewal — a rolling window is derived from that anchor. Renewal-only webhooks (same tier) intentionally do NOT reset it.
- A resource that has no admin-configured plan tier (e.g. the free tier) needs a hardcoded fallback quota table — don't assume every tier is configured in admin/site-content.

## Atomicity is the core invariant — read before touching this code
- A plain "read remaining, then write increment" (two separate statements/calls) is NOT safe for quota enforcement: concurrent requests can both read the same remaining amount and both then increment, overshooting the limit. Any check that gates real billable usage must check-and-increment as one atomic unit (e.g. an advisory-lock-guarded transaction, or a single conditional SQL statement) — never compose a separate "check" call with a later "increment" call from application code.
- A read-only, non-committal check (e.g. "is there any quota left at all before we even start this multi-step job") is fine on its own as long as the actual per-unit consumption is enforced atomically at the point of consumption, not at the upfront gate.
- For actions that reserve quota before knowing whether they'll succeed (e.g. paid AI generation), refund the reservation on failure — otherwise failed attempts silently eat into the vendor's quota.

## Idempotency for usage metered from user-triggered actions (not just webhooks)
- A "send"-type endpoint (campaign send, bulk action, etc.) that both changes a record's status AND meters billable usage is just as vulnerable to duplicate-request overcharge as a webhook — a client double-submit or naive retry is enough, no external at-least-once delivery required.
- Fix is the same shape as the webhook case: claim the state transition (e.g. draft -> sent) with a single conditional UPDATE ("WHERE status != already-final-state") in the SAME transaction as the quota consumption, so either both happen or neither does. A losing/duplicate request should detect the failed claim and return the *prior* result as a success no-op, not an error — from the caller's perspective the action already happened.
- Concurrent requests naturally serialize on the DB row lock from the conditional UPDATE: the loser's WHERE clause re-evaluates against the now-committed final state and matches zero rows, so it can never reach the quota-consumption step at all.

## Voice minutes: reserve-then-settle, not check-then-meter
- A read-only "is there any quota left" check before a multi-step async job (e.g. a campaign that places many calls in a loop) is NOT sufficient enforcement when the actual usage amount is only known much later (call duration, known only when the call ends). Calls placed between the check and the eventual metering can blow past the quota because nothing atomic ever reserved their share.
- Correct pattern: atomically RESERVE a fixed worst-case amount (via the atomic consume-quota primitive) immediately before starting each unit of work, bounded by a hard cap enforced by the underlying provider (e.g. Twilio's call `TimeLimit` parameter) so actual usage can never exceed the reservation. Once the real amount is known, refund the unused portion. If the unit of work never actually happened (e.g. the call failed to place, or a precondition failed before the reservation had anywhere to be tracked), refund the entire reservation immediately, at the point of failure — reserve only after every precondition that can fail without a record to settle against has already passed.
- Persist the exact reservation amount AND the exact billing-period key it was reserved against on the row representing that unit of work (not just "reserve now, recompute the vendor's *current* period later") — the vendor's rolling period can roll over between reservation and settlement (e.g. a tier change mid-call), and settling against the wrong period silently leaves the original period over-charged forever.
- Settlement must run for every terminal outcome, not just ones with a known usage amount — "no answer" / "busy" / "failed" calls still terminated and still owe a settlement (refund the full reservation, since 0 minutes were actually used); gating the whole settlement block on "duration is present and > 0" leaves every non-connected call's quota locked up permanently. If the provider's terminal-event webhook only fires once for genuinely-final states (confirm this from how the event was configured, e.g. Twilio's `StatusCallbackEvent=completed`), treat every delivery as "safe to settle, in full if no usage amount," not as "maybe still in progress."
- This bounds worst-case overshoot to "one reservation's worth of quota was available when this unit of work started," instead of "however many units happened to be in flight before real usage caught up."

## Idempotency for usage metered from webhooks
- Any usage counted from an at-least-once-delivered webhook/callback (duplicates and retries are normal, e.g. Twilio call-status callbacks) needs its own idempotency guard, independent of the quota mechanism — a "claim" step that atomically flips a per-event marker only once.
- The claim and the actual usage increment must happen in the SAME transaction. If they're separate steps, a failure between them (claim succeeds, increment fails) can permanently mark the event as "already handled" while the usage was never actually recorded — a subtle, hard-to-notice under-count bug.
- If that combined claim+increment transaction fails, treat it as a billing-critical error: signal the caller to retry (e.g. respond with a non-2xx status to a webhook sender that only retries on failure) rather than swallowing the error and returning success — usage that "fails silently" here is gone forever since most webhook senders don't retry after a 2xx/success response.
- Non-billing bookkeeping in the same handler (e.g. updating a display-only call status) can stay best-effort/fire-and-forget without this rigor — only the usage-affecting write needs transactional + retry treatment.
