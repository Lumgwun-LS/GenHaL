## The pattern
`storeGeneratedMedia` (server-side, for AI-generated bytes) and the client-upload endpoints
(`/ai/upload-video-url`, `/ai/upload-image-url`) both end up producing the exact same URL shape:
a presigned object-storage PUT target plus a public `https://<domain>/api/media/:objectId` URL
served by `routes/media.ts`. Because publishing code only ever consumes a `mediaUrls` string, it
is completely agnostic to whether that URL came from AI generation or a vendor's own upload — no
downstream changes were needed to support vendor uploads once the presigned-URL endpoint existed.

**Why:** keeping upload and generation on one URL shape means every existing consumer (post
create/update, all four platform publishers, share links) works unmodified.

**How to apply:** when adding a new "let the user attach their own X" flow, look for the existing
AI-generation storage helper first and mirror its output shape (presigned PUT + public GET URL)
rather than inventing a parallel media representation.

## Gotcha: ACL is not actually required for serving
`routes/media.ts` serves objects unconditionally regardless of ACL visibility (ACL only affects
the `Cache-Control` header, not access). The existing video-upload flow only sets ACL to public
as a side effect of the *analyze-video-caption* step (which downloads the file) — a photo upload
with no analysis step never gets ACL set at all, and that's fine; it still serves correctly.
